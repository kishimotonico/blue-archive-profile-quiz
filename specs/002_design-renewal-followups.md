# デザイン刷新後の改善案

デザイン刷新（wip/design-renewal）をマージする前に、Fable と Astra に設計のレビューを受けました。このブランチでは対応せず、別の作業として検討する改善案をここにまとめます。どちらのレビューも「このまま master にマージしてよい」という結論でした。

マージ後にあらためて Fable がコードと計画を読み直し、進め方と設計の方針を次のとおり改めました（2026-09-24）。

## 決めたこと

- プレイ状態は jotai をやめ、controller の `useReducer` で持つ。jotai は `allStudentsAtom`（Suspense）と永続データ（日替わりの履歴・進捗）だけに使い、Provider はアプリで1つにする。`App.tsx` の `ScopedRoute` は不要になる
- 導出できる値は状態に持たない。`score` は `calculateScore(revealedHintCount, correct)` から、`portraitState` と残りステージ数は `answered` と `revealedHintCount` から決まるので、セレクタで導出する。保存形式の `score` はそのまま残し、境界で変換する
- 日替わりの結果モーダルの自動表示（回答の1.5秒後）はやめる。回答後の画面に正誤・点数・生徒がすでに出ているので、「結果を見る」ボタンだけにする。これで `DailyQuiz.tsx` のタイマー・保留フラグ・`useIsAnyDialogOpen` の監視が消える
- `Modal` はネイティブの `<dialog>` と `showModal()` を土台にする。フォーカストラップ・Escape・top-layer・背後の inert をブラウザに任せ、手書きのトラップを消す。「開いているのは同時に1つ」の管理は `dialogRegistry` のカウント方式のままで足りる

## 進め方

1〜4 を一続きに進める案（Astra の見立て）はやめ、依存関係のある 1 と 2 だけをまとめて、あとは別々の PR に分けます。差分が全ファイルに及ぶ巨大な PR を避けるためです。

1. 開示段階の計算を quiz-core に移す（下の 5）。純粋関数の抽出だけで UI に触らず、1 で作る reducer がこの関数を使う
2. 一問の reducer を quiz-core に置き、テストだけ書く（UI は触らない）
3. controller を作り、`useQuiz` / `useRegularQuiz` / `DailyQuiz.tsx` の effect 群を置き換える。保存・復元を controller につなぎ、`ScopedRoute` を消す（下の 1 と 2）
4. 画面をモバイル用とデスクトップ用のレイアウトに分け、props を整理する（下の 3）。controller の型が固まってから
5. `Modal` を `<dialog>` にし、フリープレイの Enter キー処理をボタンへのフォーカス移動に置き換える（下の 4）。ほかと依存しないので順番は前後してよい
6. 立ち絵の描画を共通化する（下の 5 の後半）
7. 演出の実行条件を決めてから、ヒント開示のアニメーションを作る（下の 6）
8. 部品を増やすタイミングで、色と部品の使い方を決める（下の 7）

履歴・統計の保存方針は、これとは別に検討します。

各 PR で守ること: 保存済みの結果や過去の `QuizKey` は壊さない。出題関数は凍結したまま使い、保存形式は境界で変換して保つ。既存のテスト（現時点で 20 ファイル 171 件）は通したまま進める。

## 1. プレイ状態を controller にまとめる

今は `store/quiz.ts` の atom を `useQuiz` が個別に書き換えていて、復元のときは `useRegularQuiz`（`useRegularQuiz.ts:44-46`）と日替わりのページ（`DailyQuiz.tsx:50-52`）が `useQuiz` を通さず同じ atom を `useSetAtom` で直接書き戻しています。回答・復元・次の問題への切り替えのたびに、呼び出し側が状態の組み合わせを知っている必要があります。日替わりのページは useEffect が5本（初期化・進捗保存・結果保存・モーダル自動表示・フォーカス）あり、effect 同士の衝突を避けるための `isAlreadyCompleted` や `autoShowResultPending` が増えています。

quiz-core に一問の純粋な reducer を置き、モードごとの controller hook がそれを `useReducer` で持つ形にします。

- reducer の状態は判別共用体にする。例: `{ status: "playing", question, revealedHintCount } | { status: "answered", question, revealedHintCount, outcome }`。`answered` / `correct` / `score` を別々に書き換えずに済み、矛盾した状態を型で作れなくする
- `score`・`portraitState`・残りステージ数はセレクタで導出する
- controller が公開するのは「開示する」「回答する」「復元する」「次の問題へ進む」などの操作だけにして、個別の setter は外に出さない
- 準備中と読み込み失敗は controller 側の状態として持つ（reducer は「問題がある」前提で書く）
- reducer と判定関数は React に依存させない。問題の生成には、今あるバージョン別の関数をそのまま使う
- 回答の戻り値を、今の「入力欄を空にしてよいか」の boolean から、`accepted` / `unknownStudent` / `ignored` のような意味の分かる結果に変える。入力を残すか、エラーを出すかは UI 側で決める
- 日替わりとフリープレイで一問の進行ルールを共通にし、モード固有の情報（全10問の結果、今日の結果を復元済みか、など）は各 controller に置く
- `useQuiz` の `answerFeedback` / `errorKey` は controller のローカル state のままでよい

`quiz-core/types.ts` の `QuizState` は定義だけあって使われていません。reducer の状態型を決めるときに、使うか消すかを判断します。

## 2. 保存・復元と Provider

- controller が保存処理を呼ぶ。reducer 自体には書き込みや時刻の取得を入れない
- 保存は effect で状態を監視するのではなく、controller の dispatch の後に行う。「復元が終わるまでは保存しない」を、`loading` フラグの順序ではなく構造で保証する
- 確定した結果を何度保存しても重複しない。再開したときは演出を再生しない。この2つも保存処理との約束にする
- `ScopedRoute` を消し、Provider はアプリで1つにする。履歴・統計のように複数の画面から読む永続データは jotai のまま
- 問題生成用の `QuizKey`、プレイを区別するセッション ID、同じセッション内の問題 ID は、目的が違うので分けて扱う。同じ生徒が続けて出ることもあるので、`student.id` を UI のリセット条件にしない

## 3. 画面の構成と props

- `QuizScreen` の props は16個あり、そのうち11個は `useQuiz` の戻り値をそのまま渡している。表示用のデータと操作を、それぞれ小さな型に分けて渡す
- 共通の外枠の下に、モバイル用とデスクトップ用のレイアウトを1つずつ置く。モバイルの立ち絵は `HintList` の中ではなく、レイアウト側で組み合わせる
- 入力途中の文字や問題の識別子は、レイアウトの分岐より上に置く。今は回答欄を作り直す key に `scrollResetKey` と `student.id` を使っていて、画面の幅が変わっただけでも回答欄が作り直され、入力が消える。`AnswerInput` を controlled にして入力値を `QuizScreen` 側で持てば key は要らない
- ヒントボタンへのフォーカスのために、`hintButtonRef` をページから何段も受け渡している。フォーカス先は各レイアウトで決め、controller には DOM の ref を持たせない

## 4. ダイアログとドロワー

今は `Modal` とヘッダーのドロワーが、それぞれ別に Escape キーを処理しています。全身モーダルは `StudentPortrait` の中、結果モーダルはページの中で開閉を管理しています。

- `Modal` をネイティブの `<dialog>` に置き換える。ドロワーも同じ土台に乗せられるか検討する
- 「アプリ全体で開くのは1つだけ」を管理する仕組みは作らない。3ページのアプリには重すぎる。`dialogRegistry` のカウント方式で足りる
- フリープレイの「Enter で次の問題へ」は document 全体のキー入力を拾っている。回答後に「次の問題へ」ボタンへフォーカスを移せば、この処理と `useIsAnyDialogOpen` への依存が要らなくなる
- 日替わりの結果モーダルの自動表示はやめる（上の「決めたこと」）

## 5. 開示段階の計算と立ち絵の描画

- 「ヒント数 + 1 がシルエットの段階」という前提が、`QuizScreen`・`QuizPlayArea`・`portraitUtils.ts`・`useQuiz` の4か所に別々の式で書かれている。`getRevealStage()` のような純粋関数にまとめて quiz-core に置く。カードの配置や演出の状態は入れない
- `PortraitState` 型は quiz-core にあるのに、それを計算する `getPortraitState` は components 側にある。上の段階計算と一緒に quiz-core に移す
- 立ち絵の画像とシルエットの処理が、モバイルのヒント一覧、デスクトップの立ち絵パネル、全身モーダルの3か所にある。シルエットのフェードインの作り方も場所によって違う。URL・読み込み失敗時の画像・シルエットの表現だけを `PortraitImage` にまとめ、切り抜きやサイズは呼び出し側に残す
- `hooks/useRegularQuiz.ts` が `components/quiz/portraitImageUrl` を import している。hook と component の両方から使うものは、別の場所に置く

## 6. 演出

今は動きの実装が3種類あります。CSS の keyframes（開示時のきらめき、リング）、motion ライブラリ（入力欄のシェイク）、`HintList` の ref とタイマーを組み合わせた制御です。

- 技術を1種類に揃えることより、実行条件を先に決める。新しく開示したときだけ再生する。保存からの復元では再生しない。次の問題に進んだら中断する。動きを減らす設定のときは、すぐ最後の状態を出す
- 1回の開示の流れ（カードが開く、立ち絵が出る、スクロールする）は、担当する hook かコンポーネントを1つにする。必要なら motion に寄せる。ボタンのホバーやリングの単純な遷移は CSS のままでよい
- ゲームとしての開示状態はすぐに確定させる。演出が終わるのを、保存や回答の前提にしない
- 動きを減らす設定への対応は、今は CSS の演出にしか入っていない。motion のシェイクと、なめらかなスクロールにも同じ方針を当てる
- `HintList` の開示演出は、750ms のタイマーと CSS の 0.7s を手で合わせている。長さは一か所で持つ

## 7. 色と部品

- 青は装飾・文字色・白文字を載せる面・フォーカスのリングと、用途が広い。用途がぶつかる色にだけ、意味のある別名を足す。トークンをすべて作り直す必要はない
- ボタンの見た目の状態は `Button` の中にまとめ、呼び出し側の `className` は幅・配置・余白だけにする。今は「回答する」の disabled の透明度を、呼び出し側で important を付けて上書きしている
- primary ボタンのハイライト線は RGB を直書きしている。トークンから導出する
- `rounded-2xl border border-ba-border bg-white` の直書きが8か所以上ある。`.ba-card`（白い面）と `.ba-card-muted`（淡い面）程度のクラスにまとめる。背景・枠線・角丸だけにして、余白や高さまでは共通にしない

## 履歴・統計の保存方針

日替わりの結果は直近100件だけ詳細を残し、それより前はスコア別の件数にまとめています。今の統計（累計・ベスト・ランク分布）には足りていますが、連続日数や生徒ごとの成績を後から出そうとしても、まとめた分の詳細は戻りません。日替わりの結果には、回答した文字列も残していません。

- 履歴の機能を決めるときに、残す期間と項目を先に決める
- 保存の流れを「読み込み・検証・移行・保存」に揃える。今はフリープレイの進捗は Valibot で検証しているが、日替わりは旧形式からの移行のときしか検証していない
- 出題アルゴリズムの `QuizKey.version` と、保存形式のバージョンは分けて管理する

## 見送ったもの

- `useQuiz` の `answerFeedback` / `errorKey` を atom にする（Fable の提案）。今は `useQuiz` を1か所でしか呼んでいないので、ローカルの state のままでよい
- アプリ内の動きをすべて1種類の技術で書く（Fable の提案）。上の「6. 演出」のとおり、実行条件と開示の流れの担当を揃えることを優先する
- 開示ボタンに「（残り6）」のような残り数を添える。ボタンはシンプルに保ち、残り数はリングで示す
- 1〜4 を一続きの設計変更として進める（Astra の提案）。上の「進め方」のとおり PR を分ける

## 今の方針のまま、将来見直す余地があるもの

- デスクトップの立ち絵は、絵の上端に合わせてバストアップに切り抜いている（`object-cover object-top`）。切れ方は絵によって違い、生徒によっては顔が枠の上端に寄る可能性がある。崩れる生徒が見つかったら、全身を収める（`object-contain`）か、生徒ごとに切り抜く位置をデータで持つかを検討する
- 回答前のデスクトップでは、右カラムのいちばん大きな面が「?」だけになっている。リングの数字には単位がない。いま正解すると何点かを示すなど、この面の使い方は検討の余地がある
- タブレット幅（768〜1023px）はモバイル型のクイズ画面になり、ヒント一覧の下に大きな空白ができる
