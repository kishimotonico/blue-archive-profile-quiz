# デザイン刷新後の改善案

デザイン刷新（wip/design-renewal）をマージする前に、Fable と Astra に設計のレビューを受けました。このブランチでは対応せず、別の作業として検討する改善案をここにまとめます。どちらのレビューも「このまま master にマージしてよい」という結論でした。

マージ後にあらためて Fable がコードと計画を読み直し、進め方と設計の方針を次のとおり改めました（2026-09-24）。その案を Astra がもう一度レビューし、保存の契約と得点の扱いについて修正を受けています。

## 方針

このリファクタは保守的に進めない。既存構造を壊してでも、いちばん素直な設計にする。

- 今回のリファクタで互換性を守るのは、過去の `QuizKey` からの問題再現（`QuizKey.version` で世代管理している出題関数を凍結する）だけ。保存形式は変えたいときに変え、旧データは移行せず捨ててよい。日替わりの回答履歴もこの範囲に含める（今回は消えてよい）
- 日替わりの回答履歴を今後の改修でリセットしなくて済むようにする設計（保存層を「読み込み・検証・移行・保存」の流れにし、形式変更を移行関数1つで済ませる）は、このリファクタの次のタスクとして別に行う。今回はそれを妨げる作りにしなければよい
- レアケースへの処理、過度なフォールバック、回復策は入れない。「こうなると危ないから」を理由にした判断もしない
- 「今の実装がこうだから」を理由に残す構造はない。既存の props・型・ファイル配置を維持する必要はない

## 決めたこと

- プレイ状態は jotai をやめ、controller の `useReducer` で持つ。jotai は `allStudentsAtom`（Suspense。`store/students.ts` に移す）と永続データ（日替わりの履歴・進捗）だけに使い、Provider はアプリで1つにする。`App.tsx` の `ScopedRoute` から消すのはルートごとの store 生成だけで、ルートごとの ErrorBoundary と Suspense は残す（`Result.tsx` も `allStudentsAtom` を読む）
- 導出できる値は状態に持たない。`portraitState`・残りステージ数・回答後に見せるヒントの範囲は `status` と開示数から導出する。ただし得点は記録であって導出値ではない。回答を確定した時点で計算して結果に持たせ、保存済みの結果はそのまま読む
- 「回答時の使用ヒント数」と「回答後・再訪時に画面で見せるヒントの範囲」を分ける。今の `DailyQuiz` は完了済みの復元で `revealedHintCount = hints.length + 1` にして全ヒントを表示しているため、ここを混ぜると1ヒントで10点だった記録が復元後に1点扱いになる
- 日替わりの結果モーダルの自動表示（回答の1.5秒後）はやめる。モバイル・デスクトップの両方で、「結果を見る」ボタンだけにする。回答後の画面に正誤・点数・生徒がすでに出ているため。これで `DailyQuiz.tsx` のタイマー・保留フラグ・`useIsAnyDialogOpen` の監視が消える
- `Modal` はネイティブの `<dialog>` と `showModal()` を土台にする。フォーカストラップ・Escape・top-layer・背後の inert をブラウザに任せ、手書きのトラップを消す。`showModal()` は「同時に1つだけ」を保証する API ではないが、自動表示をやめればその要件自体がなくなる。`dialogRegistry` は購読者がいなくなった時点で削除する

## 進め方

1〜4 を一続きに進める案（Astra の当初の見立て）はやめ、依存関係のあるものだけをまとめて、別々の PR に分けます。差分が全ファイルに及ぶ巨大な PR を避けるためです。Astra も分割に賛成しています。

1. 日替わりの結果モーダルの自動表示をやめる（小さな UI PR）。先にやると controller が引き継ぐ制御が減る
2. quiz-core に開示段階の純粋関数と一問の reducer を置き、テストを書く（UI は触らない。下の 5 の前半と 1）。回答時のヒント数・確定結果・復元の型はこの PR で合意する
3. controller を作り、保存・復元をつなぎ、`useQuiz` / `useRegularQuiz` / `DailyQuiz.tsx` の effect 群を置き換える。両モードをつなぎ替えて旧プレイ atom の利用がなくなった時点で `store/quiz.ts` のプレイ用 atom と `ScopedRoute` の store 生成を消す（下の 1 と 2）。この PR では既存の `QuizScreen` の props に変換して渡してよい
4. 画面をモバイル用とデスクトップ用のレイアウトに分け、props を整理する（下の 3）。controller の契約は変えない
5. `Modal` を `<dialog>` にし、フリープレイの Enter キー処理をボタンへのフォーカス移動に置き換える（下の 4）。フォーカス先はレイアウトが持つ ref に依存するので、4 の後に行う
6. 立ち絵の描画を共通化する（下の 5 の後半）。4 の後が自然
7. 演出の実行条件を決めてから、ヒント開示のアニメーションを作る（下の 6）
8. 部品を増やすタイミングで、色と部品の使い方を決める（下の 7）

履歴・統計の保存方針は、これとは別に検討します。

各 PR で守ること: 出題関数は凍結したまま使う。テストは件数の維持を目的にせず、atom の内部構造を前提にしたテストは置き換える。振る舞いとして守るのは次の4つ: 保存済み10点の復元、途中再開、終了後の進捗削除、同じ生徒が続いたときの次問開始。

## 1. プレイ状態を controller にまとめる

今は `store/quiz.ts` の atom を `useQuiz` が個別に書き換えていて、復元のときは `useRegularQuiz`（`useRegularQuiz.ts:44-46`）と日替わりのページ（`DailyQuiz.tsx:50-52`）が `useQuiz` を通さず同じ atom を `useSetAtom` で直接書き戻しています。回答・復元・次の問題への切り替えのたびに、呼び出し側が状態の組み合わせを知っている必要があります。日替わりのページは useEffect が5本（初期化・進捗保存・結果保存・モーダル自動表示・フォーカス）あり、effect 同士の衝突を避けるための `isAlreadyCompleted` や `autoShowResultPending` が増えています。

quiz-core に一問の純粋な reducer を置き、モードごとの controller hook がそれを `useReducer` で持つ形にします。

- 一問の reducer の状態は `playing | answered` の2状態の判別共用体にする。例: `{ status: "playing", question, revealedHintCount } | { status: "answered", question, result }`。`result` には確定結果（正誤・回答時の使用ヒント数・確定回答・得点）を持たせる。入力エラー・演出中・モーダル表示中はこの status に増やさない
- `portraitState`・残りステージ数・回答後に見せるヒントの範囲はセレクタで導出する。プレイ中の「いま正解すると何点か」を出すなら `calculateScore(count, true)` のような明示的なセレクタにし、未回答の `correct = false` から0点を導出しない
- 型で防げるのは status と payload の整合性まで。ヒント数の範囲、回答済みへの二重 submit、次問への二重 advance は reducer の遷移規則で防ぐ
- controller が公開するのは「開示する」「回答する」「復元する」「次の問題へ進む」などの操作だけにして、個別の setter は外に出さない
- 準備中と読み込み失敗は controller 側で `loading | ready(session) | error` の判別共用体として持ち、ready の中に一問の状態を置く。`loading: boolean` / `error` / `question | null` を独立した state にすると同じ不整合を別の層で作れる。ロード完了後だけ条件付きで `useReducer` を呼ぶのは避ける（モードの reducer が ready のときだけ一問の reducer に委譲するか、ロード完了後の子コンポーネントで一問の controller を始める）
- `allStudentsAtom` のロード待ち（Suspense）と、問題生成・復元の待ち（controller の loading）は別物。後者は controller がキャンセルも含めて管理する。reducer の initializer や render の中で保存や履歴追加をしない（StrictMode や Suspense で複数回呼ばれる）
- 既存の `DailyResult` は回答文字列を保存していない。日替わりとフリープレイで同じ確定結果の型を使い、`DailyResult` にも `userAnswer` を持たせる。保存形式のバージョンを上げ、旧データは捨てる
- reducer と判定関数は React に依存させない。問題の生成には、今あるバージョン別の関数をそのまま使う
- 回答の戻り値を、今の「入力欄を空にしてよいか」の boolean から、`accepted` / `unknownStudent` / `ignored` のような意味の分かる結果に変える。入力を残すか、エラーを出すかは UI 側で決める
- 日替わりとフリープレイで一問の進行ルールを共通にし、モード固有の情報（全10問の結果、今日の結果を復元済みか、など）は各 controller に置く
- `useQuiz` の `answerFeedback` / `errorKey` は controller のローカル state のままでよい

`quiz-core/types.ts` の `QuizState` は定義だけあって使われていません。reducer の状態型を決めるときに、使うか消すかを判断します。

## 2. 保存・復元と Provider

- controller が保存処理を呼ぶ。reducer 自体には書き込みや時刻の取得を入れない
- 保存の形は「reducer が確定した保存用 snapshot を、controller の1本の effect で永続化する」にする。React の dispatch は更新後の状態を返さないので、「dispatch の直後に保存する」は実装指示にならない。避けたいのは複数の effect が独立した boolean を監視して復元・保存・演出を同時に制御する構造であって、永続化という外部同期を1本の effect が担うこと自体ではない。終了操作のようにイベント側で即時保存する箇所があるなら、通常の同期と競合しない契約を決める
- 復元中は保存しない。新規の確定結果は一度だけ作り、問題の `key.baseDate` を識別子にして保存する。再開したときは演出を再生しない。フリープレイの終了・進捗削除・画面遷移の順序もここで決める
- `ScopedRoute` のルートごとの store 生成を消し、Provider はアプリで1つにする。プレイの reset は controller の責任。履歴・統計のように複数の画面から読む永続データは jotai のまま
- ルートごとの ErrorBoundary と Suspense は残す（`allStudentsAtom` の Suspense 用）。生徒データのロード失敗からの回復策は足さない
- 問題生成用の `QuizKey`、プレイを区別するセッション ID、同じセッション内の問題 ID は、目的が違うので分けて扱う。同じ生徒が続けて出ることもあるので、`student.id` を UI のリセット条件にしない

## 3. 画面の構成と props

- `QuizScreen` の props は16個あり、そのうち11個は `useQuiz` の戻り値をそのまま渡している。表示用のデータと操作を、それぞれ小さな型に分けて渡す
- 共通の外枠の下に、モバイル用とデスクトップ用のレイアウトを1つずつ置く。モバイルの立ち絵は `HintList` の中ではなく、レイアウト側で組み合わせる
- 入力途中の文字や問題の識別子は、レイアウトの分岐より上に置く。今は回答欄を作り直す key に `scrollResetKey` と `student.id` を使っていて、画面の幅が変わっただけでも回答欄が作り直され、入力が消える。「新しい問題になった」と「幅が変わった」を区別し、前者では問題 ID に紐づけて入力とエラー表示を消し、後者では維持する。key を使うかどうかはその手段にすぎない
- ヒントボタンへのフォーカスのために、`hintButtonRef` をページから何段も受け渡している。フォーカス先は各レイアウトで決め、controller には DOM の ref を持たせない

## 4. ダイアログとドロワー

今は `Modal` とヘッダーのドロワーが、それぞれ別に Escape キーを処理しています。全身モーダルは `StudentPortrait` の中、結果モーダルはページの中で開閉を管理しています。

- `Modal` をネイティブの `<dialog>` に置き換える。React の `isOpen` とネイティブの cancel / close の同期、閉じるボタンと背景クリック、復帰先が消えた場合のフォーカスは wrapper の責任として残る。ヘッダーのドロワーも同じ土台に乗せられるか検討し、独立した Escape listener が残るなら dialog との関係を整理する
- 「アプリ全体で開くのは1つだけ」を管理する仕組みは作らない。3ページのアプリには重すぎる
- フリープレイの「Enter で次の問題へ」は document 全体のキー入力を拾っている。回答後に「次の問題へ」ボタンへフォーカスを移せば、この処理と `useIsAnyDialogOpen` への依存が要らなくなる
- 日替わりの結果モーダルの自動表示はやめる（上の「決めたこと」）。自動表示と Enter 処理が消えると `dialogRegistry` の購読者がいなくなるので、そこで registry ごと削除する

## 5. 開示段階の計算と立ち絵の描画

- 「ヒント数 + 1 がシルエットの段階」という前提が、`QuizScreen`・`QuizPlayArea`・`portraitUtils.ts`・`useQuiz` の4か所に別々の式で書かれている。`getRevealStage()` のような純粋関数にまとめて quiz-core に置く。カードの配置や演出の状態は入れない
- `PortraitState` 型は quiz-core にあるのに、それを計算する `getPortraitState` は components 側にある。上の段階計算と一緒に quiz-core に移す
- 立ち絵の画像とシルエットの処理が、モバイルのヒント一覧、デスクトップの立ち絵パネル、全身モーダルの3か所にある。シルエットのフェードインの作り方も場所によって違う。URL・読み込み失敗時の画像・シルエットの表現だけを `PortraitImage` にまとめ、切り抜きやサイズは呼び出し側に残す
- `hooks/useRegularQuiz.ts` が `components/quiz/portraitImageUrl` を import している。hook と component の両方から使うものは、別の場所に置く

## 6. 演出

今は動きの実装が3種類あります。CSS の keyframes（開示時のきらめき、リング）、motion ライブラリ（入力欄のシェイク）、`HintList` の ref とタイマーを組み合わせた制御です。

- 技術を1種類に揃えることより、実行条件を先に決める。新しく開示したときだけ再生する。保存からの復元では再生しない。次の問題に進んだら中断する。動きを減らす設定のときは、すぐ最後の状態を出す
- 1回の開示の流れ（カードが開く、立ち絵が出る、スクロールする）は、担当する hook かコンポーネントを1つにする。必要なら motion に寄せる。ボタンのホバーやリングの単純な遷移は CSS のままでよい
- ゲームとしての開示状態はすぐに確定させる。演出が終わるのを、保存や回答の前提にしない
- 動きを減らす設定への対応は、今は CSS の演出にしか入っていない。motion のシェイクと、なめらかなスクロールにも同じ方針を当てる
- `HintList` の開示演出は、750ms のタイマーと CSS の 0.7s を手で合わせている。長さは一か所で持つ

## 7. 色と部品

- 青は装飾・文字色・白文字を載せる面・フォーカスのリングと、用途が広い。用途がぶつかる色にだけ、意味のある別名を足す。トークンをすべて作り直す必要はない
- ボタンの見た目の状態は `Button` の中にまとめ、呼び出し側の `className` は幅・配置・余白だけにする。今は「回答する」の disabled の透明度を、呼び出し側で important を付けて上書きしている
- `rounded-2xl border border-ba-border bg-white` の直書きが8か所以上ある。`.ba-card`（白い面）と `.ba-card-muted`（淡い面）程度のクラスにまとめる。背景・枠線・角丸だけにして、余白や高さまでは共通にしない

## 履歴・統計の保存方針

日替わりの結果は直近100件だけ詳細を残し、それより前はスコア別の件数にまとめています。今の統計（累計・ベスト・ランク分布）には足りていますが、連続日数や生徒ごとの成績を後から出そうとしても、まとめた分の詳細は戻りません。

- 履歴の機能を決めるときに、残す期間と項目を先に決める
- 保存の流れを「読み込み・検証・移行・保存」に揃え、形式変更を移行関数1つで済ませる。これはリファクタの次のタスク（上の「方針」）
- 出題アルゴリズムの `QuizKey.version` と、保存形式のバージョンは分けて管理する

## 見送ったもの

- `useQuiz` の `answerFeedback` / `errorKey` を atom にする（Fable の提案）。今は `useQuiz` を1か所でしか呼んでいないので、ローカルの state のままでよい
- アプリ内の動きをすべて1種類の技術で書く（Fable の提案）。上の「6. 演出」のとおり、実行条件と開示の流れの担当を揃えることを優先する
- 開示ボタンに「（残り6）」のような残り数を添える。ボタンはシンプルに保ち、残り数はリングで示す
- 1〜4 を一続きの設計変更として進める（Astra の当初の提案）。上の「進め方」のとおり PR を分ける。Astra も再レビューで分割に賛成した
- アプリ共通の `activeDialog` を持つ（Astra の当初の提案）。結果モーダルの自動表示をやめれば、守る要件が小さくなり不要になる

## 今の方針のまま、将来見直す余地があるもの

- デスクトップの立ち絵は、絵の上端に合わせてバストアップに切り抜いている（`object-cover object-top`）。切れ方は絵によって違い、生徒によっては顔が枠の上端に寄る可能性がある。崩れる生徒が見つかったら、全身を収める（`object-contain`）か、生徒ごとに切り抜く位置をデータで持つかを検討する
- 回答前のデスクトップでは、右カラムのいちばん大きな面が「?」だけになっている。リングの数字には単位がない。いま正解すると何点かを示すなど、この面の使い方は検討の余地がある
- タブレット幅（768〜1023px）はモバイル型のクイズ画面になり、ヒント一覧の下に大きな空白ができる
